Message Processing ​

This page covers how data moves through an OIE channel, from initial receipt through transformation and delivery.

About message data ​

A message in OIE represents one complete unit of data traveling through a channel's source and destinations. Each message is broken down into individual connector messages, one per connector it passes through. So a channel with a source and two destinations generates three connector messages for every inbound message.

It is important to note that a single inbound payload does not necessarily equal a single message. If the source connector's batch processor is enabled, one incoming file or data stream can be split into many discrete messages. For instance, a file with 100 HL7 v2.x messages could produce either 1 or 100 messages depending on the batch configuration.

Message metadata ​

Metadata captures key information about each message without including the actual content:

  • Message ID. A unique integer assigned per channel. Used for organizing entries in the Message Browser and linking related connector messages.
  • Connector Metadata ID. A numeric identifier for each connector. The source is always 0, and destinations are numbered starting from 1.
  • Status. Tracks where each connector message stands in the processing pipeline (see Message Statuses below).
  • Timestamps. Each connector message records a received date (when data was committed to the database). Destinations also track a send date and response date, which can help diagnose performance and latency.
  • Custom Metadata Columns. User-defined database columns that extract and store selected values from the message, making them visible and searchable in the Message Browser.

Message content ​

As data travels through a channel, multiple snapshots of it are captured at different stages. Each connector maintains its own set of content versions.

Source connector content ​

Content TypeDescription
RawThe inbound message after attachment extraction but before any preprocessor modification
Processed RawThe message after the preprocessor script has had a chance to modify it
TransformedThe internal (typically XML) representation after serialization. Only present when a filter or transformer is configured
EncodedThe final outbound form after deserialization from the internal representation
ResponseWhatever gets sent back to the originating system once all processing is complete

Destination connector content ​

Content TypeDescription
RawThe starting data for the destination, which is always a copy of the source's encoded output
TransformedThe internal representation after the destination's own serialization. Only present when a filter or transformer is configured
EncodedThe final outbound form after the destination's transformer and deserialization
SentA snapshot of the destination connector properties (dispatch parameters and envelope) captured before the send attempt
ResponseThe reply received back from the external system
Response TransformedThe internal representation of the response. Only present when a response transformer is configured
Processed ResponseThe response in its final form after response transformation and deserialization

INFO

Each destination receives a copy of the source's encoded data as its raw input. Destinations do not receive data from each other in a daisy-chain fashion. Even with three destinations, every one of them gets the same source encoded output as their starting point.

Other stored content ​

The content types above are the message payload at its various stages. The engine persists several other kinds of content alongside them, which is why maps and errors survive to be viewed in the Message Browser long after processing finished:

Content TypeDescription
Source MapThe source map as it stood for this message
Connector MapThe connector map for this connector message
Channel MapThe channel map for this message
Response MapThe response map, holding responses keyed by destination
Processing ErrorErrors raised during filtering, transformation, or dispatch
Postprocessor ErrorErrors raised by the postprocessor script
Response ErrorErrors raised while handling the destination's response

The three error types are stored separately rather than merged, so an error in the postprocessor is distinguishable from one thrown during transformation.

Message statuses ​

StatusMeaning
RECEIVEDData has been persisted but is still being actively processed
FILTEREDThe message was rejected by a filter and will not continue
TRANSFORMEDThe transformer has completed successfully; for the source connector this is the final status
SENTThe destination successfully dispatched the message
QUEUEDThe message is waiting in the destination queue, either for initial delivery or retry
ERRORSomething went wrong during processing
PENDINGThe message is waiting to begin processing

Source processing steps ​

  1. The source connector receives an inbound message or data stream.
  2. If the batch processor is active, the data may be divided into multiple messages. The remaining steps repeat for each one.
  3. The attachment handler runs, pulling out and separately storing any attachment content.
  4. What remains is saved as the raw data.
  5. The preprocessor script runs, and its output is saved as the processed raw data.
  6. The processed raw data is serialized into the inbound data type's internal format (usually XML).
  7. Filters evaluate the message. If it is rejected, processing skips ahead to the Final Processing Steps.
  8. The transformer modifies the data as needed.
  9. The result is saved as the transformed data.
  10. The data is deserialized from the outbound data type's internal format back into a concrete format (e.g., HL7, EDI).
  11. This output is saved as the encoded data.

INFO

When no filter or transformer is present, no transformed or encoded content will exist. The raw (or processed raw) data carries forward directly.

  1. The encoded data is handed off to the first destination connector in each destination chain.

Destination processing steps ​

These steps run independently for every destination connector the message reaches.

  1. The destination starts with the source's encoded output as its raw data.
  2. This raw data is serialized into the inbound data type's internal format.
  3. Filters evaluate the message. If rejected, processing stops for this destination. If other destinations remain in the chain, they continue. Once all chains finish, the Final Processing Steps run.
  4. The transformer modifies the data as needed.
  5. The result is saved as transformed data.
  6. The data is deserialized from the outbound data type's internal format into the final outbound format.
  7. This output is saved as encoded data.

INFO

When no filter or transformer is present, no transformed or encoded content will exist. The raw data carries forward directly.

  1. The destination connector captures a snapshot of its dispatch properties as sent data, then dispatches the message to the external system.
  2. Any reply from the external system is captured as the response data.
  3. If a response transformer is configured, the response is serialized into the response inbound data type's internal format.
  4. The response transformer runs.
  5. Its output is saved as response transformed data.
  6. The response is deserialized from the response outbound data type's internal format into its final form.
  7. This is saved as processed response data.

Final processing steps ​

Processing reaches this point once every destination chain has completed, or immediately if the message was filtered or errored at the source level.

  1. The post processor script runs and may return a response value.
  2. The source connector selects a response to send back to the originating system. This could be an auto-generated reply, the response from a specific destination, whatever the post processor script returned, or a custom value from the response map.
  3. The chosen response is saved as the source connector's response data and delivered to the originating system if applicable.

Message attachments ​

Attachments allow you to separate large or binary content from the message body early in the pipeline. They are tied to the overall message rather than to individual connector messages, and the extraction occurs before even the preprocessor script runs.

When a destination dispatches data, any stored attachments are automatically spliced back in. Because attachment content is only stored once, rather than being duplicated across each connector's raw, transformed, and encoded snapshots. This approach can significantly reduce memory consumption.

Message queuing ​

When a destination has queuing enabled:

  1. Depending on the queue mode, messages are either placed directly into a persistent queue or attempted first and queued on failure
  2. A background thread retries queued messages at configurable intervals
  3. Queue settings include:
    • Retry interval (milliseconds between attempts)
    • Rotate queue (move failed messages to the back of the queue)
    • Retry count (maximum retry attempts before marking as ERROR)
    • Thread count (number of parallel queue processing threads)

Queue modes ​

The Queue Messages setting on the destination offers three choices:

ModeBehavior
NeverNo queuing. Retries still apply according to the retry count setting
On FailureAttempt an immediate send when the queue is empty, and queue only if that fails
AlwaysQueue first, then send from the queue thread

INFO

Queueing depends on the message storage mode. With storage set to Raw, Metadata, or Disabled, queueing is not supported, and the Administrator shows a warning next to the setting when On Failure or Always is selected. If you need queueing, the channel needs a fuller storage mode.

Additional queue settings on the same panel:

SettingEffect
Thread Assignment VariableGroups queued messages onto threads by the value of a variable, so related messages keep their relative order. Only available when queueing is on and thread count is above 1
Regenerate TemplateRebuilds the destination's template from the message each time it is sent from the queue, rather than reusing what was built when it was queued
Include Filter/TransformerRe-runs the destination filter and transformer on each queue attempt instead of only on the first

Batch processing ​

The batch processor lets a source connector break a single inbound payload into many individual messages. When paired with a streaming-capable connector (such as the File Reader or TCP Listener in MLLP mode), this enables processing of very large files (even gigabytes) without loading the entire payload into memory at once.

To turn on batch processing, set Process Batch to Yes in the source connector's settings. The specific splitting behavior is controlled by the Batch Properties within the source inbound data type configuration.

While batch messages are moving through a channel, three additional source map variables become available:

  • batchId. Identifies the overall batch; all messages from the same inbound payload share this value
  • batchSequenceId. A counter starting at 1 that increments with each message in the batch
  • batchComplete. A boolean flag that is true only for the final message in the batch
