Architecture Overview ​

The Open Integration Engine (OIE) is an open source standards-based healthcare integration engine that enables interoperability between two systems by accepting incoming information packets, called messages, and processing them according to rules you provide. It speeds message routing, filtering, and transformation between health-info systems using various message formats (e.g., HL7, X12, EDI, DICOM, XML).

Core concepts ​

Channels ​

Channels are the fundamental building blocks of OIE. A channel is an interface you configure to receive data from a source, take actions on that data (filter, transform, extract), and send it out to one or more destinations.

┌──────────┐    ┌─────────────────────────────────────────┐    ┌─────────────────┐
│  Source   │───>│            OIE Channel                  │───>│  Destination     │
│  System   │    │  Source Connector → Filter/Transformer  │    │  System(s)       │
└──────────┘    │               → Destination Connector(s) │    └─────────────────┘
                └─────────────────────────────────────────┘

Each channel has general properties including a unique ID, name, and description. Channels can also be configured with code template library links, library resources, deploy/start dependencies (to control deployment order), attachment handler settings, message storage and pruning settings, and custom metadata columns.

Connectors ​

A channel consists of multiple connectors:

  • Source Connector. Gets data into OIE from an external system. Every channel has exactly one source connector. Source connectors may also include a source queue (when ON, messages are queued and a response is sent immediately before processing completes), a batch processor (to split incoming data into multiple messages), a response selector (to choose which response to return), and a max processing threads setting (to control concurrent processing).
  • Destination Connectors. Sends data out to external systems. A channel has at least one, and may have multiple destination connectors. Each destination has an enabled flag and a wait for previous destination setting that determines its chain membership. Destinations also include a response transformer for processing responses received from external systems.

For example, you may receive data over HTTP, then write it out to a file and insert pieces of it into a database.

See Channels and Connectors and Connector Reference for details.

Filters ​

A filter decides whether a message should proceed to the next step or not. A filter returns true (accepted) or false (filtered). Filters are comprised of multiple rules, joined by AND or OR operators.

  • If the source connector filters out a message, it will not be processed by any destination connectors.
  • If a destination connector filters out a message, other destinations may still process it.

See Filters and Transformers for details.

Transformers ​

A transformer modifies a message, converts it from one format to another, and extracts pieces for later use. A transformer has an inbound data type and an outbound data type (e.g., HL7 v2.x to JSON). Transformers are comprised of multiple steps, each of which modifies or extracts data.

See Filters and Transformers for details.

Data types ​

A data type tells a filter/transformer how to parse a certain format. The inbound data type serializes raw data into an internal representation that filters and transformers can work with. The outbound data type deserializes transformed data back into the actual outbound format.

The internal representation varies by data type. For example, HL7 v2.x data is serialized into an E4X XML object, JSON data becomes a JavaScript Object, and Raw data remains a Java String with no serialization.

Supported data types include:

  • Delimited Text
  • DICOM
  • EDI / X12
  • HL7 v2.x
  • HL7 v3.x
  • JSON
  • NCPDP
  • Raw
  • XML

See Data Types and Formats for details.

Message processing lifecycle ​

The raw inbound message enters OIE, is received by the source connector, filtered, transformed, then encoded and sent to the destination connector(s). Each destination can apply its own filters and transformers.

Source processing steps ​

  1. A message or stream of data is received by the source connector
  2. The batch processor decides whether to split the data into multiple messages. If so, the remaining steps are repeated for each message returned by the batch processor.
  3. The attachment handler extracts and/or stores attachment data
  4. The post-attachment-handler content is stored as raw data
  5. Content runs through the preprocessor script and is stored as processed raw data
  6. Content is serialized to the internal representation of the inbound data type (e.g., XML)
  7. Content runs through the filter and is either accepted or filtered. If filtered, flow jumps directly to the Final Processing Steps.
  8. Content runs through the transformer, where it may be modified
  9. Post-transformer content is stored as transformed data
  10. Content is deserialized from the outbound data type into the actual outbound format
  11. Content is stored as encoded data
  12. The resulting content is passed to the first destination connector of each destination chain

INFO

If no filter or transformer is configured, there will not be any transformed or encoded data. In that case, the content used from here on will be the raw data (or processed raw data if a preprocessor modified it).

Destination processing steps ​

These steps are repeated for each destination connector that a message flows through:

  1. The encoded content from the source connector is used as raw data
  2. Content is serialized to the internal representation of the inbound data type
  3. Content runs through the filter and is either accepted or filtered. If filtered, flow stops for this destination. If there are more destinations in the current chain, these steps repeat for the next one. Otherwise, flow proceeds to the Final Processing Steps.
  4. Content runs through the transformer, where it may be modified
  5. Post-transformer content is stored as transformed data
  6. Content is deserialized from the outbound data type into the actual outbound format
  7. Content is stored as encoded data
  8. The destination connector builds a message from all available previous content, stores it as sent data, and sends it to the outbound system
  9. A response is received and stored as response data
  10. If a response transformer is configured, the response is serialized to the internal representation of the response inbound data type
  11. The response runs through the response transformer, where it may be modified
  12. Post-response-transformer content is stored as response transformed data
  13. The response is deserialized from the response outbound data type into the actual outbound format
  14. The response is stored as processed response data

INFO

If no filter or transformer is configured, there will not be any transformed or encoded data. In that case, the content used from here on will be the raw data only.

Final processing steps ​

INFO

This point is reached when all destination chains have finished processing the message. If the message was filtered or errored out on the source connector, flow jumps directly to this step.

  1. The post processor script is executed. It can return a response that the source connector may use.
  2. The source connector decides what response to send back to the originating system, if any. This may be an auto-generated value, the response payload from a destination connector, a response returned from the post processor script, or a custom value from the response map.
  3. The selected response is stored and sent back to the originating system.

Destination chains ​

A channel's destinations are grouped into one or more destination chains. Each chain processes simultaneously with respect to other chains, but within a chain, messages flow through each destination in order. This allows parallel processing across chains while maintaining order within a chain.

Message data ​

Messages and connector messages ​

A message refers to a single overall dispatch of data through the source connector and destination connectors within a channel. Messages are further divided into connector messages, the portions of the message that flow through a single connector. For example, a channel with two destinations will have three connector messages per message: one for the source connector and one for each destination.

Messages do not always correspond 1-to-1 with incoming data. If a source connector has a batch processor enabled, a single incoming file containing 100 HL7 v2.x messages could be split and processed as 100 separate messages.

Message metadata ​

Each message carries metadata used for tracking and diagnostics:

  • Message ID. A unique integer ID per channel, used to group connector messages together in the message browser.
  • Connector Metadata ID. Each connector has its own ID. The source connector is always 0. Destination connectors start at 1 and increment for each destination added.
  • Status. The current processing state of each connector message (e.g., RECEIVED, QUEUED, SENT, ERROR).
  • Timestamps. Every connector message stores a received date. Destination connectors also store send date and response date. Comparing these timestamps helps diagnose performance issues.
  • Custom Metadata Columns. User-defined columns that extract data from messages for display and searching in the message browser.

Message content types ​

As a message flows through a channel, different versions of the data are stored for each connector:

Source connector: Raw, Processed Raw, Transformed, Encoded, Response

Destination connector: Raw, Transformed, Encoded, Sent, Response, Response Transformed, Processed Response

INFO

When a message flows from the source to destination connectors, the source's Encoded Data becomes the Raw Data for each destination. Raw Data is not daisy-chained from destination to destination. Every destination receives the same source Encoded Data as its starting point.

Message attachments ​

An attachment is a piece of data extracted from the raw incoming message and stored separately. Extraction happens at the very beginning of the message lifecycle, before the preprocessor script runs. Because multiple copies of the message data are stored as it flows through a channel (raw, transformed, encoded), storing large pieces as attachments reduces memory usage. Attachments are automatically re-inserted into outgoing data when a destination connector dispatches.

See Message Processing for details.

Channel scripts ​

Four special scripts are associated with each channel:

  • Deploy Script. Runs once right before a channel is deployed.
  • Preprocessor Script. Runs once for every message, after the attachment handler has optionally extracted data, but before the source filter/transformer. Used to modify the incoming message.
  • Post Processor Script. Runs once for every message, after the source connector and all destinations have completed (excluding asynchronous processes like the destination queue), but before a response is sent back to the originating system. Has access to responses from all executed destinations and can return a custom response for the source connector to use.
  • Undeploy Script. Runs once right before a channel is undeployed.

Administration interfaces ​

  • Administrator. A Java Swing desktop client for managing channels, viewing messages, configuring settings, and monitoring the system. Connects to the server over HTTPS using a RESTful API. Requires a compatible launcher; see Desktop Administrator for the available options.
  • Web Administrator. A browser-based administrator installed as the Web Support extension and served by the engine's own embedded Jetty. Read/write against the same REST API, so it and the desktop client can be used against one engine at the same time. Requires 4.6.0.
  • Command Line Interface (CLI). A terminal-based client for scripting and headless administration. Uses the same REST API as the Administrator.

Extensions ​

OIE uses a plugin architecture where connectors, data types, and other features are loaded as extensions. Extension types include:

  • Connectors. Source and destination communication protocols
  • Data Type Plugins. Message format parsers and serializers
  • Server Plugins. Background services and event handlers
  • Transmission Mode Providers. Frame-level protocol handling (e.g., MLLP)

Extensions are discovered at runtime, so one install serves both the desktop and web administrators. A growing set of open source extensions is available beyond those bundled with the engine. See Plugins and Extensions.
